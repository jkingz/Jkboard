## System boundaries

```
/ (client redirect) → /landing
                          └─ /sign-in, /sign-up → Better Auth forms
                                                       │
proxy.ts (cookie presence only, nodejs runtime) ───────┤
                                                       ▼
(dashboard)/layout.tsx ── auth.api.getSession() ──► redirect("/sign-in") if null
        │
        ├── getWorkspaceData() ────── drizzle/neon-http ──► Postgres
        │
        └── getMemberByUserId() ───── drizzle/neon-http ──► Postgres
                 │
                 ├── null ──► WorkspaceAccessNotice, nothing else renders
                 └── row  ──┐
                             ▼
        initialData + currentMember props ──► DashboardShell ──► JkboardProvider (client ctx)
                                                        │
        ┌───────────────────────────────────────────────┘
        ▼  every page calls useJkboard()
   actions.* ──► db/actions/*.ts ──► requireMembership() first ──► db ──► revalidatePath("/", "layout")
```

The database is imported **only** from `src/db/**` and `src/lib/auth.ts`. No client component may
import `db` — `src/db/index.ts` is marked `server-only`, which is the enforcement.

## Storage model

- Records are **mutated in place**, not append-only. The one append-ish behaviour is `task.reference`,
  generated by a database sequence.
- `task.reference` defaults to `'TSK-' || lpad(nextval('task_reference_seq')::text, 4, '0')` and is
  `UNIQUE`. It exists purely so the UI never displays a 36-char UUID. **The database generates it; the
  client never supplies it.**
- **No JSONB columns.** Every queryable field is a typed column, so reads are plain selects — there is
  no "the values live in a JSON blob" trap here.
- Dates: `start_date` / `due_date` are `date` with `mode: "string"` (no timezone). Timestamps are
  `withTimezone: true`. The query layer converts to `YYYY-MM-DD` via UTC (`toISODate`,
  `src/db/queries/jkboard.ts:32`).
- **Every `toISODate` reads the UTC calendar.** There are three — `src/data/jkboard.ts:90`,
  `src/db/queries/jkboard.ts:32` and `scripts/seed-data.ts:14` — and all three derive the
  `YYYY-MM-DD` string from `getUTC*`. That is what makes `daysUntil(dateFromToday(n)) === n`:
  the write half and the read half of a `date` column agree on which day it is, in any zone. The
  helpers were split across the local and UTC calendars until this change, which is why the
  round-trip is asserted in `tests/platform/unit/dates.unit.test.ts` rather than trusted.
- `task.position` is an integer, **descending** — new tasks get `min(...) - 1` so they land at the top
  of a column.

## Persistence schema

DDL from `src/db/schema/*.ts`. Columns people commonly assume exist but do not:

- **`member` has no `name`, `email`, or `image` column.** Identity lives in `user`; `member` holds
  only membership. Reading `member.email` is a runtime failure, not a type error that fires early.
- **`task.description` is a column with no reader.** It is written by `createTaskAction` /
  `updateTaskAction` and selected nowhere: `taskSchema` (`src/data/jkboard.ts:60`) has no
  `description` field, so it never enters the view model and is never rendered. `project.description`
  **is** read and rendered (`projects-grid.tsx:275`, `project-board.tsx:127`). Do not generalise one
  to the other.
- **`task.completed_at` is set by application logic, not the database.** `updateTaskAction`
  (`src/db/actions/tasks.ts:119`) writes it when status is `completed`, nulls it when `todo`, and
  writes a literal `sql\`null\`` for `in-progress` / `in-review` — deliberately preserving a prior
  completion timestamp for tasks moved back from `completed`.

Tables:

- **`user`**: `id` text PK, `name`, `email` unique, `email_verified` bool, `image`, `created_at`,
  `updated_at`. Better Auth owns this table.
- **`session`**: `id` text PK, `expires_at`, `token` unique, `user_id` → `user.id` cascade,
  `ip_address`, `user_agent`, timestamps. Indexed on `user_id`.
- **`account`**: `id` text PK, `account_id`, `provider_id`, `user_id` → cascade, `password`, token
  columns, `scope`, timestamps. Indexed on `user_id`. Email/password only — no OAuth provider is
  configured.
- **`verification`**: `id` text PK, `identifier`, `value`, `expires_at`, `created_at`. Indexed on
  `identifier`.
- **`member`**: `id` uuid PK, `user_id` → `user.id` cascade, `role` text default `'Member'`, `status`
  enum (`active` | `invited` | `away`) default `invited`, `joined_at`, `last_active_at`. Unique on
  `user_id`. **No name/email columns.**
- **`project`**: `id` uuid PK, `name`, `key` unique (2–4 letters, stored uppercased), `description`
  default `''`, `status` enum (`planning` | `active` | `on-hold` | `completed`) default `planning`,
  `color` default `'var(--chart-1)'`, `owner_id` → `member.id` **`on delete restrict`**, `start_date`,
  `due_date`, timestamps. Indexed: status, owner_id, due_date.
- **`project_member`**: composite PK `(project_id, member_id)`, both cascade. The join table; no
  surrogate key, no timestamps.
- **`task`**: `id` uuid PK, `reference` text unique (sequence default), `project_id` → cascade,
  `title`, `description` default `''`, `status` enum default `todo`, `priority` enum
  (`urgent` | `high` | `medium` | `low`) default `medium`, `assignee_id` → `member.id`
  **`on delete set null`**, `due_date`, `position` int default 0, `completed_at`, timestamps.
  Indexed: project_id, status, due_date, assignee_id, (project_id, status).

The two delete behaviours are load-bearing and asymmetric:

- `project.owner_id` is **RESTRICT** — a member who still owns a project cannot be deleted.
- `task.assignee_id` is **SET NULL** — a departing member leaves their tasks in place, unassigned.

`removeMemberAction` (`src/db/actions/members.ts:144`) therefore transfers owned projects to another
member *before* deleting the `user` row, and throws if there is nobody left to transfer to. Note it
deletes from **`user`**, not `member` — the membership and join rows go by cascade.

## Auth and tenancy

- **Identity**: Better Auth session cookie → `auth.api.getSession()`, backed by `user`.
  Role/ownership lives in the `member.role` **column**, which nothing currently reads.
- **Two authorities, for two different questions.**
  `src/app/(dashboard)/layout.tsx:26` decides whether a *page renders* and whose membership to hand
  the client as `currentMember`. `requireMembership()` (`src/db/actions/session.ts`) decides whether
  a *mutation may run*, and returns the caller's `member.id` or throws. Both read the same session
  and the same unique `member_userId_uidx`, so the page and the action cannot disagree about who is
  calling.
- **What the guard is not**: authorization. Under one shared workspace any member may write any row,
  so "there is a session and it belongs to a member" is the whole check. Role checks are
  [specs/02](../specs/02-role-model-and-demo-scoping.md), and per-row ownership is recorded in
  [specs/01](../specs/01-session-identity-and-action-guards.md) → "Later increments".
- `src/proxy.ts` is an **optimistic** check only. It calls `getSessionCookie(request)` — presence, not
  validity — because the proxy bundle cannot import the database. A stale cookie passes it and is
  caught by the layout. It must never redirect signed-in users away from `/sign-in`; that produces an
  infinite `/sign-in → /dashboard → /sign-in` loop.

## Invariants

Numbered. They get cited by number in commits and reviews.

1. **The database is never imported from a client component.** Enforced by `server-only` in
   `src/db/index.ts` and `src/lib/auth.ts`, plus `"use server"` in `src/db/actions/*.ts`. Violating it
   ships credentials to the browser.
2. **`member` has no identity columns.** Name and email are read by joining `user`. A query selecting
   `member.name` does not exist.
3. **`task.reference` is database-generated and client-supplied values are ignored.** A caller cannot
   choose a reference.
4. **Every mutation ends in `revalidatePath("/", "layout")`.** Omitting it leaves the client context
   showing stale data after a successful write, with no error to trace.
5. **`proxy.ts` never redirects a session-bearing request away from `/sign-in` / `/sign-up`.**
   Violating it produces an infinite redirect loop that flickers between the loading state and the
   form.
6. **Project ownership transfers before member deletion.** `owner_id` is `ON DELETE RESTRICT`;
   skipping the transfer makes `removeMemberAction` throw at the database.
7. **Every mutation identifies its caller before it touches the database.** Each action exported from
   `src/db/actions/` awaits `requireMembership()` ahead of its first write; `setTaskStatusAction`
   inherits it by delegating to `updateTaskAction`. Skipping it does not break anything a user can
   see — it silently reopens the anonymous-write hole `specs/01` closed.

**Test coverage of these invariants:** 2, 3 and 6 are asserted against `information_schema` on a real
database, in `tests/platform/integration/invariants.integration.test.ts` and
`column-contracts.integration.test.ts`. 1, 4 and 7 are covered in the unit tier by
`module-boundaries.unit.test.ts` and `action-revalidation.unit.test.ts`, which read the source tree.
5 is covered by `proxy.unit.test.ts`, which calls `proxy()` with real `NextRequest`s in-process — no
browser and no running app were needed for any of the three.

Read the strength of each. 1, 4 and 7 are enforced **structurally**: the test walks the files and asserts
the rule still holds, so it catches the edit that breaks the rule and nothing else — a runtime path
that reaches the same data without passing a gated module fails no assertion. For 7 that gap is real:
no test executes the guard. It has run exactly once, on a hand-driven replay of one action against a
production build with an unverifiable session cookie (`specs/01` → Verification), which is evidence about
that request and not a gate. 5 is behavioural but
only for `proxy()` itself, which is an optimistic cookie-presence check; it cannot say anything about
what a valid session does downstream. And nothing calls `removeMemberAction` on an owner of a project,
so 6 is verified as a column constraint (`ON DELETE RESTRICT`), never as the app following the rule.

**Zero-caller note:** `countOwnedProjects()` and `assertMemberExists()` in
`src/db/actions/projects.ts` are exported but have **no callers** — `removeMemberAction` inlines its
own lookup instead. Verified by grep across `src/` and `scripts/`. They are dead exports.

**Stale hardcoded data:** `src/data/jkboard.ts` also exports module-level seed arrays `members`,
`projects` and `tasks` plus a `taskSeeds` input. These are **not** the live workspace. Dashboard
pages get data from `useJkboard()`, and the selectors (`getTaskStats`, `getWorkload`, …) are always
called with an explicit `source` argument, so the arrays are only live defaults for code that passes
nothing — which is why the unit tier supplies its own fixtures.

**No component reads them.** `src/components/command-search.tsx` used to import the seed `projects`
array directly; it now reads the store via `useJkboard()`, like every other consumer. The arrays are
still live defaults for code that passes nothing — which is why the unit tier supplies its own
fixtures. Treat any import of those three arrays as a bug unless the target is a fixture or a test.

**Planned and absent:** none. Nothing is planned, so nothing is listed here.

## Background work

None. No queue, worker, or cron. `scripts/` contains only `seed.ts`, `seed-data.ts` and
`seed-auth.ts`, all invoked manually.

- **Who consumes this in production:** nothing — no background work exists.

## Pages and caching

Pages, from the filesystem: `/` (client redirect to `/landing`), `/landing`, `/sign-in`, `/sign-up`,
five `/errors/*` pages, and under `(dashboard)`: `/dashboard`, `/projects`, `/projects/[id]`, `/tasks`,
`/calendar`, `/users`, `/settings/{user,account,notifications,connections,billing}`. Plus the
framework's `not-found.tsx`, `loading.tsx` and `favicon.ico`. The build output confirms this list and
labels `ƒ Proxy (Middleware)`.

`(dashboard)` is `dynamic = "force-dynamic"` — nothing under it is prerendered or cached. **No cache
tags are used anywhere.** Landing, auth and error pages are static (`○`).

UI that reads a column nothing writes yet: none. Every rendered field has a writer.
